# Script Studio Prosody UI Design

**目标**

把 Script Studio 的语气与朗读参数做成真正可扫、可改、可复核的控制台 UI，而不是零散的字段堆叠。

本次围绕两件事展开：

1. 提高信息密度
2. 稳住视觉秩序

在不新增接口、不改变后端协议的前提下，把以下字段完整接到 Studio：

1. `tone`
2. `strength`
3. `pauseAfter`
4. `prosody.pace`
5. `prosody.pitch`
6. `prosody.energy`
7. `prosody.pauseMsAfter`

**设计上下文**

依据项目现有 `.impeccable.md`：

1. 这是内容生产控制台，不是展示型页面
2. 风格应该专业、冷静、可信赖
3. 默认 light-first，减少装饰性干扰
4. 信息密度高，但主操作与关键状态必须一眼可见

## 现状问题

当前 Studio UI 处于“半接通”状态：

1. 卡片视图已有 `tone` 与 `strength`
2. 表格和预览仅有 `tone`
3. `prosody` 完全没有展示
4. 编辑弹窗只能编辑 `tone`
5. 不同视图使用不同的信息密度和展示语言

这会带来三个坏味道：

1. **晦涩性**
   - 用户看不到已落库的关键参数
2. **冗余与不一致**
   - 不同视图展示不同字段，认知切换成本高
3. **不必要复杂性**
   - 数据已经在，但用户得靠猜测去理解 TTS 行为

## 设计原则

1. 一套视觉语言，多处复用
   - 列表卡片、表格、预览和编辑弹窗共享同一套参数命名与层级

2. 主信息与次信息分层
   - `角色 / tone / 台词文本` 是主层
   - `strength / pause / prosody` 是次层

3. 高密度但不拥挤
   - 不走“badge 墙”路线
   - 用紧凑规格条承载次级信息

4. 编辑要顺手，不要像调试面板
   - 参数字段做成操作型表单，不让用户面对一堆原始 JSON

## 方案对比

### 方案 A：参数标签墙

做法：

1. 所有字段都用 Badge 展示
2. 编辑弹窗把全部字段平铺

优点：

1. 实现快
2. 信息全

缺点：

1. 扫描噪音大
2. 视觉秩序差
3. 很容易长成“日志面板”

### 方案 B：规格条方案（推荐）

做法：

1. `tone` 保持主标签
2. 其余字段收成统一的参数规格条
3. 各视图共享同一套字段顺序和文案

优点：

1. 密度高但不乱
2. 非常符合控制台气质
3. 后续再加字段也有稳定位置

缺点：

1. 需要抽出一个共享展示组件

### 方案 C：双层折叠

做法：

1. 默认只显示一部分参数
2. 其余放入展开区

优点：

1. 首屏更简洁

缺点：

1. 牺牲高密度可扫
2. 不利于批量复核

## 推荐方案

采用 **方案 B：规格条方案**。

它最符合现有设计上下文：

1. 信息优先
2. 视觉克制
3. 控制台感强
4. 可扩展但不过度设计

## 一、统一参数规格条

### 结构

定义一套共享的“朗读参数规格条”：

1. `强度 52`
2. `停顿 1.0s`
3. `语速 0.91`
4. `音高 -0.10`
5. `能量 0.42`
6. `尾停 1000ms`

### 视觉层级

1. `tone` 用主标签承载
2. 参数规格条使用更轻的文本对比和更紧凑的间距
3. 缺失字段不显示占位，不制造空噪音

### 好处

1. 扫一眼就知道“这句怎么念”
2. 不需要阅读 JSON 结构
3. 复用后所有视图语言一致

## 二、列表卡片优化

目标文件：

1. `ScriptSentenceCard.tsx`

### 改法

卡片顶部收成两层：

1. 第一层
   - 序号
   - 角色
   - `tone`
   - 段落位置信息
2. 第二层
   - 朗读参数规格条

### 视觉要求

1. 第一层更稳重、更醒目
2. 第二层像控制台里的辅助指标，不喧宾夺主
3. 文本区保持左对齐，不做居中装饰

## 三、表格视图优化

目标文件：

1. `ScriptSentencesTable.tsx`

### 改法

保留现有列结构，不新增多个参数列。

把“语气”列升级为：

1. 第一行显示 `tone`
2. 第二行显示紧凑参数摘要

例如：

`平静`
`强 52 · 停 1.0s · 速 0.91`

### 原因

1. 保持横向可读性
2. 不让表格宽度失控
3. 适合批量扫视

## 四、预览弹窗优化

目标文件：

1. `ScriptPreviewModal.tsx`

### 改法

预览里每句也带同款规格条，但权重略低于正文。

### 原因

预览的主要任务是快速审稿：

1. 台词文本仍然是主角
2. 参数是辅助理解，不应比正文更抢眼

## 五、编辑弹窗优化

目标文件：

1. `EditSentenceModal.tsx`

### 改法

弹窗结构分成两个区块：

1. 基础信息
   - 台词内容
   - 角色
   - 语气
2. 朗读参数
   - 强度
   - 句末停顿（秒）
   - 语速
   - 音高
   - 能量
   - 额外尾停（毫秒）

### 交互原则

1. 留空即不覆盖
2. 前端只做轻量归一化
3. 文案用业务语言，不直接暴露技术黑话

## 六、数据与类型改动

本次不新增接口，只补前端接线：

1. `apps/web/src/lib/types.ts`
2. `apps/web/src/app/books/[id]/studio/script/components/types.ts`
3. `apps/web/src/app/books/[id]/studio/script/page-container/hooks/actions/useScriptSentenceActions.ts`

需要让本地状态与保存 payload 都承载：

1. `prosody`
2. `strength`
3. `pauseAfter`

## 七、测试策略

### 重点覆盖

1. 编辑弹窗能提交完整字段
2. `useScriptSentenceActions` 能把字段送进 `updateScriptSentences()`
3. 本地状态会同步更新
4. 卡片、表格、预览能稳定展示规格条

### 不做

1. 不为样式像素做快照测试
2. 不在本次引入 E2E

## 结论

这次 UI 优化的关键不是“多显示几个字段”，而是把朗读参数从零散的附属信息，提升为 Studio 里可扫、可控、可复核的控制台语言。用统一规格条承载次级参数，是兼顾信息密度与视觉秩序的最小优雅方案。
