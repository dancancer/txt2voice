# txt2voice 项目纠偏与推进路线图（2026-03-08）

## 1. 项目目标（重要的话说三遍）

**我们的目标是：把小说/文本可靠地转换成“内容正确、角色正确、情绪正确、音频稳定、可人工校正”的有声书。**

**我们的目标是：把小说/文本可靠地转换成“内容正确、角色正确、情绪正确、音频稳定、可人工校正”的有声书。**

**我们的目标是：把小说/文本可靠地转换成“内容正确、角色正确、情绪正确、音频稳定、可人工校正”的有声书。**

上面这句话不是宣传语，而是后续所有设计、开发、评审和验收的唯一判断标准。

如果某项工作不能直接提升以下任一能力，就不应该排在高优先级：

1. 原文内容保真
2. 台本结构正确
3. 音频生成稳定
4. 自动质检可信
5. 人工复核高效
6. 远端运行可复现

### 1.1 项目最终验收标准

当我们说“项目达到阶段性目标”时，至少要满足下面这些条件：

- 原文到台本：不漏内容、不重复抽取、不错误拆分对话与旁白。
- 台本到音频：角色、语气、停顿和内容与台本一致，且批量生成稳定。
- 质检与复核：自动质检能发现大部分明显问题；人工复核能快速定位并纠正剩余问题。
- 运行环境：本地与远端行为一致，不依赖隐性手工修复，不因为 GPU 抢占或配置漂移而失真。
- 交付闭环：每本书都有明确的状态、日志、验收结论与回退路径。

## 2. 项目现状与目标之间的差距

下面先列“大块差距”，不纠缠细节，但不能遗漏关键面。

### 2.1 原文 -> 台本 的语义保真链路不可靠

当前最核心的问题不是音频，而是台本本身就可能错。

已确认的具体症状：

- 台本会漏掉原文内容。
- 同一段引号对白可能被旁白复述一次，再单独作为对白提取一次，出现重复抽取。
- LLM 可能对原文做压缩、总结、改写，而不是严格映射。
- 长段文本在生成时容易触发 token 截断，JSON 虽能修复格式，但无法修复已丢失的语义。

本质问题：

- Prompt 契约不够强，没有强约束“完整覆盖、禁止重复、禁止改写、禁止摘要”。
- 生成后缺少确定性校验层，只校验 JSON，不校验语义保真。
- 分段策略虽然存在，但仍有较大段落进入 LLM，导致截断概率和抽取歧义升高。

### 2.2 台本 -> 音频 的生成稳定性不够

当前音频不是不能生成，而是“能生成”和“稳定生成”之间还有明显差距。

已确认的具体症状：

- 远端 VoxCPM 在较高并发时会出现 `500 Internal Server Error`。
- 同一本书经常需要二次、三次补跑才能收敛到 100%。
- TTS 服务的健康检查与真实可生成状态不完全等价，曾经出现“health 绿了但 synth 不可用”的情况。

本质问题：

- 并发策略没有按 provider 的真实承载能力调优。
- 首轮全量生成与失败重试的策略不够保守。
- 运行时 GPU 资源可能被其他模型服务抢占，导致表面在线、实际异常。

### 2.3 自动质检没有覆盖真正关键的问题面

当前自动质检不是完全没价值，但它还不是“你听一下就知道不对”的那种质检。

已确认的具体症状：

- 明显的内容错误没有及时进入人工复核队列。
- 质检结果很大程度上依赖生成后的台本，而不是直接对照原文。
- 当缺少真实的 CER / speaker similarity / 音频信号时，系统会退化到 heuristic，容易过于乐观。

本质问题：

- 当前 QC 主要做“音频 vs 台本”的检查，不是“原文 vs 台本 vs 音频”的三方校验。
- Script 层没有独立质检，因此台本先错了，后续音频 QC 也会跟着错。
- Deep Gate 仍偏启发式统计，不是真正意义上的听感质量判断。

### 2.4 人工复核工作台没有成为默认可信兜底

当前 review 页存在，但还没成为“发现问题 -> 定位单句 -> 决策返工”的主战场。

已确认的具体症状：

- 如果没跑 QC 或 QC 没产出 `manual_review_items`，复核页就没有可操作结果。
- 用户听出明显问题时，系统未必能把对应句子提前送进人工复核队列。
- 人工复核视角仍偏结果聚合，缺少“原文 / 台本 / 单句音频 / 问题原因”四合一工作流。

本质问题：

- 复核入口依赖 QC，而 QC 本身还不够可信。
- 复核工作台的信息密度不够高，不能快速支持“定位 -> 判断 -> 修复”。

### 2.5 本地 / 远端 / 运行时 之间仍然存在漂移风险

当前我们已经把远端拉回到能跑通的状态，但风险并没有彻底消失。

已确认的具体症状：

- 远端曾存在旧 worker、无效 LLM key、GPU 抢占、端口冲突等历史残留。
- 远端代码目录存在未提交改动，部署一致性依赖人工判断。
- 某些运行时问题是“代码没变，但环境变了”导致的。

本质问题：

- 运行环境还没有被完全产品化、模板化、标准化。
- 真正影响质量的运行时约束（例如 GPU 隔离、provider 并发、重试策略）还没有沉淀成强规则。

### 2.6 迭代机制还不够“目标对齐”

如果继续按零散修 bug 的方式推进，系统会反复偏离项目目标。

本质问题：

- 缺少明确的阶段目标与退出标准。
- 缺少阶段回顾机制。
- 缺少“每阶段一个核心块”的约束，容易多线并行后失焦。
- 缺少统一的分支 / PR / 合并纪律，导致阶段成果难以结算。

## 3. 逐步推进的分阶段解决方案

原则：**每个阶段只打一个大块。**

每个阶段必须包含：

1. 问题分析
2. 设计结论
3. 执行计划
4. 验收标准
5. 分支与 PR 规则

---

## 阶段 1：原文 -> 台本 正确性重建

### 3.1 阶段目标

把“原文保真”重新变成第一性原则，解决漏内容、重复抽取、对白/旁白边界错误。

### 3.2 分析结论

当前项目最大的问题不是 TTS，也不是 QC，而是台本层缺少“确定性守门员”。

只要台本允许：

- 漏原文
- 重复提取
- 改写摘要
- 对白旁白边界漂移

那么后面的所有音频、质检、人工复核都会建立在错误地基上。

因此第一阶段必须优先做“原文 -> 台本”的结构化约束和校验，而不是继续调音频或调阈值。

### 3.3 执行计划

#### 3.3.1 收紧 Prompt 契约

明确要求 LLM：

- 必须完整覆盖原文
- 不允许省略、总结、压缩、改写
- 同一段原文只能映射一次
- 引号内对白不能同时出现在旁白句和对白句中
- 返回结果必须能追溯到原文切片

#### 3.3.2 引入台本确定性校验器

在落库前增加 Script Validator，至少检查：

- 原文覆盖率
- 重复对白检测
- 引号句是否被重复抽取
- 旁白是否包含整段对白原句
- 输出文本总量与原文量级是否严重偏离

若校验失败：

- 当前段直接标记失败
- 进入重试或人工复核，而不是直接落库

#### 3.3.3 重做分段策略

现有“按字数切段”还不够，必须增加：

- 按引号密度切段
- 按句子数量切段
- 按对白密度切段
- 对高风险段做更小粒度拆分

目标不是少分段，而是保证每段足够稳定，减少 LLM 截断和结构漂移。

#### 3.3.4 增加回归测试

至少新增四类测试：

- 漏内容样例
- 重复对白样例
- 对白/旁白混抽样例
- 长段截断样例

### 3.4 验收标准

- 对已知问题样本，台本不再漏段、不再重复对白。
- 同一原文在多次运行下句子数波动显著收敛。
- 失败段会被拦下，不再直接污染库内 `script_sentences`。

### 3.5 分支与 PR

- 分支名建议：`codex/phase-1-script-correctness`
- 阶段完成后：提交单独 PR
- PR 合入主干后，下一阶段必须从主干重新切新分支

## 阶段 2：台本 -> 音频 生成稳定性收敛

### 3.6 阶段目标

让音频生成从“可以跑完”变成“稳定跑完”。

### 3.7 分析结论

当前问题主要集中在 provider 真实承载能力和运行时资源争用上。

结论：

- 首轮全量生成不应该默认高并发。
- provider 需要区分稳定并发策略。
- 失败重试应该有明确的补跑模式，而不是重复全量撞库。
- TTS 健康检查必须包含真实 synth，而不是只看 `/api/health`。

### 3.8 执行计划

#### 3.8.1 Provider 并发分级

给 `indextts / cosyvoice / voxcpm` 配置独立的：

- 默认并发
- 最大并发
- 首轮并发
- 重试并发

#### 3.8.2 两阶段生成策略

- 第 1 轮：保守批量生成
- 第 2 轮：只重跑失败项
- 第 3 轮：单句低并发补跑

#### 3.8.3 运行时资源隔离

明确：

- 远端 `qwen35` 不与 TTS 常驻共机
- GPU 使用策略写入 runbook
- TTS 真实 synth 检查成为上线前必做步骤

#### 3.8.4 音频验收数据沉淀

为每次整书生成记录：

- 首轮成功率
- 补跑次数
- 每 provider 失败类型
- 平均句级耗时

### 3.9 验收标准

- 全书首轮成功率显著提升
- 单句补跑可稳定收敛到高完成率
- 不再出现“health 绿但 synth 不可用”的假健康状态

### 3.10 分支与 PR

- 分支名建议：`codex/phase-2-audio-reliability`
- 阶段完成后：提交单独 PR
- 合入后再切下一阶段分支

## 阶段 3：自动质检从“音频体检”升级为“原文-台本-音频三方校验”

### 3.11 阶段目标

让自动质检真正能抓到用户耳朵能听出来的明显问题。

### 3.12 分析结论

当前 QC 的核心缺陷不是阈值，而是基准不对。

现在更多是在做：

- 音频 vs 台本

但真正应该做的是：

- 原文 vs 台本
- 台本 vs 音频
- 原文 vs 音频（通过 ASR / 结构信号间接完成）

如果不加 Script QC，台本错了以后，音频 QC 只能“围着错误继续判断”。

### 3.13 执行计划

#### 3.13.1 增加 Script QC

新增台本质检维度：

- 原文覆盖率
- 重复对白率
- 对白/旁白边界冲突
- 句子异常压缩率

#### 3.13.2 调整 Fast Gate 默认策略

当缺少真实 `CER` / `speakerSimilarity` 信号时：

- 不再默认乐观放行
- 至少降级到 `repair`
- 对高风险句直接进入 `manual_review`

#### 3.13.3 增强音频侧真实信号

优先补强：

- ASR 文本准确率
- speaker similarity
- clipping / loudness / silence

减少 heuristic 的权重，避免“猜着放行”。

#### 3.13.4 把明显问题推进人工复核队列

对于以下情况直接进人工复核：

- Script QC 失败
- 台本覆盖率异常
- 对白重复抽取
- 高风险句多次重跑仍失败

### 3.14 验收标准

- 明显缺字、重复对白、错抽旁白等问题能够进入复核队列。
- QC 对高风险句的召回率显著提升。
- 用户主观试听发现的问题，与系统复核队列开始出现明显重合。

### 3.15 分支与 PR

- 分支名建议：`codex/phase-3-quality-gate-upgrade`
- 阶段完成后：提交单独 PR
- 合入后再切下一阶段分支

## 阶段 4：人工复核工作台重构为真实作业台

### 3.16 阶段目标

让人工复核成为可靠兜底，而不是“有时候能看，有时候没东西”。

### 3.17 分析结论

当前复核页的核心问题不是“UI 漂亮不漂亮”，而是“作业信息不够完整”。

人工复核必须在同一视图里看到：

- 原文片段
- 台本句子
- 单句音频
- 自动质检原因
- 建议修复动作

### 3.18 执行计划

#### 3.18.1 单句工作台视图

每条复核项要直接展示：

- 原文上下文
- 当前台本
- 对应音频播放器
- 失败原因 / signalValues / primarySignal

#### 3.18.2 批量处置能力

支持：

- 一键标记通过
- 一键进入返工
- 一键要求重新生成台本
- 一键重试音频

#### 3.18.3 复核结果反写

人工决策必须能回写：

- 任务状态
- issue 状态
- 后续返工队列
- 最终验收结论

### 3.19 验收标准

- 听到有问题时，可以在 1 分钟内定位到对应单句。
- 复核项能直接推动返工，而不是停留在“记录问题”。

### 3.20 分支与 PR

- 分支名建议：`codex/phase-4-review-workbench`
- 阶段完成后：提交单独 PR
- 合入后再切下一阶段分支

## 阶段 5：环境标准化、验收自动化与节奏治理

### 3.21 阶段目标

把“能跑”变成“可复现、可回归、可持续推进”。

### 3.22 分析结论

如果环境和节奏不标准化，前面四个阶段做出来的成果仍然会被运行时漂移慢慢侵蚀。

### 3.23 执行计划

#### 3.23.1 本地 / 远端运行标准化

固化：

- `.env` 最小配置模板
- GPU 运行约束
- compose 端口策略
- 队列命名空间规则

#### 3.23.2 验收脚本化

至少沉淀：

- 健康检查脚本
- 真实 synth 检查脚本
- 完整流程验收脚本
- 结果导出脚本

#### 3.23.3 阶段性报告与回归机制

每个阶段都输出：

- 目标
- 已完成项
- 未完成项
- 新发现问题
- 下阶段建议优先级

### 3.24 验收标准

- 环境恢复和验收可以按 runbook 重复执行。
- 同一测试文本在本地与远端的行为差异显著缩小。
- 新阶段开始前，团队能清楚知道为什么做、做什么、怎么验收。

### 3.25 分支与 PR

- 分支名建议：`codex/phase-5-runtime-governance`
- 阶段完成后：提交单独 PR
- 合入后再切下一阶段分支

## 4. 阶段回顾与方向校准机制

这一部分不是可选项，而是必须执行的项目纪律。

### 4.1 每个阶段结束时必须做一次正式回顾

回顾必须回答四个问题：

1. 我们这阶段做的事，是否直接推动了项目目标？
2. 当前阶段的工作，哪些是真正有效的？哪些只是缓解症状？
3. 当前阶段暴露了哪些新问题？
4. 剩余规划里，下一阶段最该做哪个块？为什么？

### 4.2 回顾输出模板

每次回顾都必须形成书面结论，至少包括：

- 阶段目标是否完成
- 验收结果
- 发现的问题列表
- 风险列表
- backlog 重排结果
- 下一阶段目标

### 4.3 优先级重排规则

当发现新问题时，必须重新审视剩余规划，并按下面顺序排序：

1. 是否直接影响“原文保真”
2. 是否直接影响“音频稳定”
3. 是否直接影响“自动质检可信度”
4. 是否直接影响“人工复核效率”
5. 是否直接影响“运行可复现性”

只有排完这个优先级，才能确定下一阶段目标。

### 4.4 分支 / PR / 合并纪律（强制执行）

每个阶段都必须遵守以下流程：

1. 从主干签出新的阶段分支。
2. 在开始当前轮次执行前，先在 `docs/task/` 创建本轮 task 文档，明确记录目标、范围、验收标准、风险、预期产物与不做事项。
3. 当前阶段只做与本阶段目标直接相关的工作。
4. 当前轮次在进入完成态之前，必须执行项目当前规定的代码质检工具，并达到“通过”状态；未通过不得进入 handoff、PR 或下一轮。
5. 当前轮次执行完成后，必须更新 `docs/handoff/` 下对应的 handoff 文档，记录本轮变更、验证结果、遗留问题、风险判断与下一轮建议。
6. 当前阶段完成后，提交一个完整 PR。
7. PR review 通过并合入主干后，关闭当前阶段分支。
8. 下一阶段必须重新从主干切新分支，不允许继续在旧分支上叠加。

推荐分支命名：

- `codex/phase-1-script-correctness`
- `codex/phase-2-audio-reliability`
- `codex/phase-3-quality-gate-upgrade`
- `codex/phase-4-review-workbench`
- `codex/phase-5-runtime-governance`

### 4.5 代码质检纪律（强制执行）

每一轮都必须通过代码质检，这是进入 handoff、PR 和下一轮的前置条件。

#### 4.5.1 执行时机

代码质检至少要在以下时间点执行：

- 当前轮次主要改动完成后
- 更新 handoff 文档之前
- 提交 PR 之前

#### 4.5.2 执行要求

- 必须使用项目当前规定的代码质检工具。
- 质检结果必须为“通过”；如果存在 warning/fail，需要先处理，再进入下一步。
- 如果工具本身异常、误报或被外部环境阻塞，必须在 handoff 中明确记录原因、影响范围和临时结论，不能默默跳过。

#### 4.5.3 文档记录要求

- 在 task 文档中，要写明本轮计划执行的代码质检项。
- 在 handoff 文档中，要写明实际执行的代码质检命令、结果、是否通过、是否存在阻塞。

### 4.5 task / handoff 文档纪律（强制执行）

这条纪律和分支纪律同级，不能省略。

#### 4.5.1 每一轮执行前必须创建 task 文档

每轮开始前，在 `docs/task/` 新建当前轮次文档，建议命名：

- `YYYY-MM-DD-round-N-<slug>.md`

每份 task 文档至少要包含：

- 本轮目标
- 本轮范围
- 本轮不做的事
- 关键假设
- 验收标准
- 风险与回滚点
- 预期产物

如果 task 文档没有创建，就视为这一轮还没有正式开始。

#### 4.5.2 每一轮执行完成后必须更新 handoff 文档

每轮完成后，在 `docs/handoff/` 更新 handoff 文档，建议命名：

- `phase-X-<slug>-handoff.md`

每次更新至少要包含：

- 本轮已完成内容
- 代码 / 配置 / 数据变更点
- 已执行验证
- 未解决问题
- 当前风险判断
- 建议的下一轮目标

如果 handoff 没更新，就视为这一轮没有完成交接，不能直接进入下一轮。

#### 4.5.3 task 与 handoff 的关系

- task 文档回答：这一轮“准备做什么”。
- handoff 文档回答：这一轮“实际上做成了什么，还剩什么问题”。

两者必须成对出现，缺一不可。

## 5. 立即执行建议

如果现在就开始推进，推荐严格按下面顺序执行：

1. 阶段 1：先修台本正确性
2. 阶段 2：再收敛音频稳定性
3. 阶段 3：再升级自动质检
4. 阶段 4：再强化人工复核工作台
5. 阶段 5：最后固化环境与治理机制

理由很简单：

- 台本是上游真相
- 音频依赖台本
- 质检依赖台本和音频
- 人工复核依赖质检
- 治理机制负责把前面四项稳定下来

顺序错了，系统会一直在错误的地基上“优化”。
